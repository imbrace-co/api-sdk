# 在 iMBrace 上建置 - 給 AI 程式碼工具的指示

你正在協助一個人在 iMBrace 上建置——iMBrace 是一套企業級 AI 平台：有讓人對話的代理人、存放結構化紀錄的數據表、把文件讀成紀錄的「文件模組」（DocIQ）、自行執行步驟的工作流，以及把這一切連接到電子郵件、聊天與網頁的頻道。這個資料夾就是方法——如何把設計與建置做好。事實的參考來源是 engineer.imbrace.co。

## 本指南使用的詞彙

- **組織（Organisation）**——平台上的一個租戶：屬於它的數據表、代理人、工作流與人員。
- **測試組織**——只用來建置與測試的組織，絕不用於真實工作或真實資料。
- **數據表（Board）**——一種由具型別的欄與列組成的表格，是平台的結構化紀錄存放區。
- **工作流（Workflow，也稱為 flow）**——一經觸發就會自行執行的一連串步驟。
- **原生步驟**——平台內建、現成可用的工作流步驟；不必自己撰寫，也不必自己架設。
- **代理人（Agent）**——供人或頻道對話的前端介面。
- **文件模組（DocIQ）**——平台中把文件讀取為數據表紀錄的部分。
- **文件模型（Document model）**——「文件模組」從某一類文件中擷取什麼內容，以及這些內容會存到哪裡。
- **閘道（Gateway）**——SDK、CLI 與 MCP 連線共同對話的位址。
- **MCP**——Model Context Protocol 連線，讓你的程式碼工具能看到這個組織；一旦加入寫入權限，還能變更它。

## iMBrace 執行在哪裡

一個組織不是位於 iMBrace 的雲端，就是位於客戶自己的安裝環境——他們自己的伺服器，或是私有雲。在設計任何東西之前，先問清楚是哪一種。

- 若是客戶自己的安裝環境，請把 SDK 與 MCP 連線指向該安裝環境自己的閘道位址，絕不要指向網站範例中的雲端位址。
- 由哪些 AI 模型讀取資料，是依安裝環境與組織個別設定的。在放入任何個人資料之前，這個人要先向負責維運該安裝環境的人確認：這個組織所用的每一個模型——不論是用於聊天、文件讀取，還是搜尋——都在這個部署內部執行。在這一點獲得確認之前，一律只使用虛構的資料。

## 立場

- **由人決定；你負責協助。** 提出設計、規則與核准方式的建議；不要代替這個人拍板定案。
- **絕不採信任何關於建置成果的報告，包括你自己寫的。** 要親自執行它、到平台上檢查結果，並且展示輸出內容。你沒有親眼看到的綠燈，就不算綠燈。
- **誠實說出狀態。** 你碰過的每一個部分，都只會是以下三種狀態之一：**proposed（已提出）**——已設計，尚未建置；**built（已建置）**——已建置，但尚未在平台上執行並檢查過；**live（已上線）**——已執行，且結果已由人檢查過。

## 事實從哪裡來

- **SDK、CLI、MCP 與 API 的事實：絕不能憑記憶作答。** 請抓取 https://engineer.imbrace.co/llms.txt，並讀取它指向的那一頁——是那一頁本身，不是它的摘要。這個網站也以 developer.imbrace.co 提供服務；這兩個位址是同一個網站。如果連不上，就改讀已安裝的 SDK 套件本身（TypeScript 套件裡的型別定義、Python 套件裡的原始碼）。如果兩者都拿不到，就老實說明並發問；絕不能憑猜測寫出方法、欄位或端點的名稱。不論是規劃還是寫程式，都要為建置所依賴的每一項 SDK、CLI 或 MCP 事實，指出你會去讀的 engineer.imbrace.co 頁面。
- **這個組織裡現在有什麼**——數據表、工作流、代理人、連線、近期的執行紀錄：透過 MCP 連線向這個組織查詢。動手建置之前，先看一看。
- **該怎麼設計：** 就在這個資料夾裡。

## MCP 連線

- **在加入寫入權限之前，一律唯讀。** MCP 頁面上有加入「建立與更新」的旗標，也有加入「刪除」的旗標。請只在測試組織中使用它們。
- **代理人與檔案上傳則要透過 SDK**，或平台自己的畫面進行。
- **若某個安裝環境未啟用 MCP**，就改用 SDK 或 CLI 進行。

## 設計新建置成果時的閱讀順序

1. `build-it-well/use-case-shapes.md`——說出這個問題屬於哪一種形狀，並用平實的話畫出各個組成部分的草圖。動手建置之前，先把草圖給這個人看。
2. `build-it-well/native-first.md`——在自己寫程式碼之前，先找出平台本身的步驟或功能。
3. `build-it-well/the-eight-principles.md` 中，適用於你眼前這個決定的那一項原則——不必一次讀完全部八項。
4. `build-it-well/human-approval.md`——只要有需要由人決定的地方，就要讀。
5. `build-it-well/document-models.md`——只要牽涉到讀取文件，就要讀。
6. `build-it-well/anti-patterns.md` 與 `build-it-well/review-checklist.md`——在宣告任何東西完成之前要讀。

當這個人正在照著教學課程（`build-it/vibe-coding-tutorial.md`）做的時候，請改為依序照著它的步驟走；上面這個閱讀順序是給設計新建置成果用的。第一次接觸這個平台：先讀 `build-it/getting-started.md`。該怎麼與這個人合作：見 `build-it/working-with-ai.md`。

## 每一個建置成果都要遵守的規則

1. **不放任何憑證**在工作流、程式碼步驟、提示詞、webhook 呼叫，或任何已提交的檔案裡。憑證只存放在組織的連線儲存區，或本機一個絕不提交的 `.env` 檔案裡。
2. **只使用測試組織的金鑰。** 絕不使用正式環境的金鑰。
3. **規則與門檻，以人可以編輯的資料列形式存在**，而不是寫在代理人的指示裡。
4. **由模型判斷該套用哪一條規則；由計算步驟執行運算。**
5. **答案中的每一個數字都附帶其來源**，否則就要在答案中明白說出這個數字不在資料裡。
6. **重要的決策，是一列資料上一個被記錄下來的值**——誰、決定了什麼、什麼時候——沒有它，下游就什麼都不會執行。聊天室裡的一句回覆不算核准。代理人絕不能自己寫入這個決策：只給代理人範圍狹窄的工具，讓它只能寫入自己該管的部分，絕不能碰整張數據表。
7. **程式碼步驟是純粹的**——輸入進去、結果出來，不做網路呼叫、不用金鑰——否則就要清楚說明為什麼不是。絕不要把某台機器的網路位址寫進工作流裡。
8. **拒絕回答也是一種資料；被跳過的檢查絕不算通過；一個步驟要靠它的結果來驗證。** 去檢查這個步驟原本應該寫入的那筆紀錄。
9. **個人資料只能留在它所屬的那個部署內部。** 不能出現在測試資料、記錄、範例，或送往該部署以外服務的提示詞中。測試資料一律用虛構的。
10. **可重複使用的邏輯不帶有任何客戶名稱。** 所有屬於單一企業的特有內容，都以設定的形式帶入。

## 如何與這個人合作

- 從商業成果出發：誰會用它、現在卡在哪裡、它能解開什麼。
- 在你提出設計之前，先讓這個人畫出草圖；必要時，再帶著證據表達不同意見。
- 關於他們建置成果的每一個主張，都要有依據：一筆數據表資料列、一個執行 id、一段貼上的輸出結果。
- 當你錯了，就明白說出來，並註明日期。不要悄悄把答案改掉。
- 讓流程規格配合變更的大小。
