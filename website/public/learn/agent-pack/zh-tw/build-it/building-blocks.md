# 基本組成元件

iMBrace 上的每一個使用案例，不論看起來有多不一樣，都是用同樣的五樣東西建置而成：一張數據表、一個代理人、一個文件模型、一個工作流，以及一個頻道。本頁會為每一樣東西命名、說明它的用途，並指出它在產品中的位置，讓你第一次打開訓練用組織時，側邊欄上不會有任何東西是個謎。最後會說明延伸其中一樣東西、或把它交給別人的三種方式：技能、MCP 連線，以及安裝模組。

## 一張數據表

數據表是一張你自己定義的結構化表格——由列與具型別的欄組成，就像一份輕量版的 CRM 表。它的用途是存放一個建置需要記住的任何東西：一份退貨申請清單、一份標好價格的報價單，或是一組可供他人編輯的規則。

在側邊欄中，這位於**「知識模組」（Knowledge）> 「數據表」（DataIQ）**之下（SDK 及其權限範圍稱它為 board，也稱 databoard；英文產品名稱則是 DataIQ）。其他每一個元件都會讀取或寫入某張數據表：工作流的每個步驟、代理人唯一那個範圍很窄的工具，以及文件模型自己擷取出的結果，最終都會落在數據表上。

畫面：一張數據表以列與具型別欄位的形式開啟
*1 「知識模組」（Knowledge）> 「數據表」（DataIQ）。2 這張數據表的具型別欄位。*

讓一張數據表值得信賴的習慣：把商業人員可能需要調整的規則——門檻值、費率、上限——放進數據表中，變成一列可編輯的資料，絕不要放進代理人自己的指示裡。[八大原則](../build-it-well/the-eight-principles.md)說明了原因。

用程式碼實作：[數據表](https://engineer.imbrace.co/zh-tw/reference/board/)。

## 一個代理人

代理人是一個人或一個頻道會與之對話的介面。它的用途是進行對話本身：理解對方在要求什麼，並呼叫正確的工具去執行。

在側邊欄中，這位於**「行動模組」（Actions）> 「AI智能助手」（AgentIQ）**之下。使用者是透過頻道找到代理人的，而它是靠呼叫一個工作流來行動——也就是下方會提到的其中一項技能——任何對數據表的讀取或寫入，實際上都發生在那裡。

畫面：AI智能助手的「啟用中的 AI」分頁，一張卡片一個助手
*1 「行動模組」（Actions）> 「AI智能助手」（AgentIQ）。2 Sales Quoting 代理人的卡片。*

讓一個代理人值得信賴的習慣：只給它一個範圍很窄的工具，對應它必須做的那一件事，絕不給它整張數據表，這樣它就能記錄一筆申請，但永遠無法自己寫下核准這筆申請的決定。[人工核准](../build-it-well/human-approval.md)說明了為什麼代理人絕不能自己寫下這個決定。

用程式碼實作：[AI 代理人](https://engineer.imbrace.co/zh-tw/reference/ai-agent/)。

## 一個文件模型

文件模型會告訴擷取功能該從一份檔案中取出什麼內容。它的用途是把一份非結構化的文件——一張發票、一份表單、一張掃描的裝箱單——轉換成數據表能容納的結構化欄位。

在側邊欄中，這位於**知識模組 > 「文件模組」（DocIQ）**之下的**「文件模型」（Document Models）**分頁。它擷取出來的內容會變成數據表上的資料列，而同一張數據表接著會被工作流或代理人讀取。

畫面：文件模組的「文件模型」分頁，開啟其中一個模型的擷取欄位
*1 知識模組 > 「文件模組」（DocIQ） > 「文件模型」（Document Models）。2 該模型的欄位表。*

讓一個文件模型值得信賴的習慣：先採用平台本身的預設模型，之後才考慮自己另外寫一個，並讓擷取功能對準單一數據表自己的欄位，而不是讓模型的選擇隨機發生。[文件模型](../build-it-well/document-models.md)說明了應該依照什麼順序去嘗試。

用程式碼實作：[Document AI](https://engineer.imbrace.co/zh-tw/sdk/document-ai/)。

## 一個工作流

工作流（也稱為 flow）是一經觸發就會自動依序執行的一連串步驟。它的用途是把實際的工作，依固定、可檢核的順序完成：讀取一張數據表、執行一項計算、等待某人做決定、發送一則訊息。

在側邊欄中，這位於**行動模組 > 「流程營運模組」（FlowOps）**之下（SDK 及其權限範圍稱它為 workflow；英文產品名稱則是 FlowOps）。工作流會讀取並寫入數據表，也可以是代理人所呼叫的唯一一項工具，並且既能由數據表的變動啟動，也能由頻道事件啟動。

畫面：流程營運模組的工作流清單
*1 行動模組 > 「流程營運模組」（FlowOps）。2 流程營運模組的工作流清單。*

讓一個工作流值得信賴的習慣：先用平台本身現成的步驟建置，任何你自己必須寫的步驟都保持單純——只根據拿到的值做運算，不持有任何屬於自己的憑證。[原生優先](../build-it-well/native-first.md)說明了這麼做能帶來什麼好處。

用程式碼實作：[工作流](https://engineer.imbrace.co/zh-tw/reference/workflow/)。

## 一個頻道

頻道是一個人實際接觸到代理人的地方——一個網站聊天視窗、WhatsApp、電子郵件，或另一個已連接的通訊應用程式——也是回覆訊息會送達的地址。

在側邊欄中，這位於**行動模組 > 「連接模組」（ConnectIQ）**之下的**「渠道設定」（Channels）**分頁。頻道是與代理人展開對話的方式，工作流也可以把頻道的某個事件當成自己的觸發條件。

畫面：連接模組的「渠道設定」分頁，列出網頁小工具與各通訊頻道
*1 行動模組 > 「連接模組」（ConnectIQ） > 「渠道設定」（Channels）。2 網頁小工具的頻道清單。*

讓一個頻道值得信賴的習慣：把它的登入資訊，設定成組織自己的連線，只設定一次，絕不讓它以一個值的形式存在於工作流裡。像代管郵件服務這種需要有人登入的連線，由一個人針對整個組織設定一次；郵件伺服器連線則用伺服器自己的詳細資料設定一次即可。[原生優先](../build-it-well/native-first.md)說明了為什麼一個流程裡不該帶有任何憑證。

用程式碼實作：[頻道](https://engineer.imbrace.co/zh-tw/reference/channel/)。

## 延伸並交付它們的三種方式

### 技能——代理人能做什麼

技能是把一個工作流交給代理人，當成它可以呼叫的一個具名工具。它的用途是把代理人實際能做的事，延伸到對話之外——記錄一筆資料、查詢某項資訊、執行一項計算——一律透過工作流進行，絕不直接把數據表交給代理人。

在代理人的設定中，這位於**「行為設定」（Behavior Settings）**分頁下的**「功能」（Skills）**區塊裡（畫面上標示為「功能」，也就是本課程所稱的技能；SDK 的完整流程指南裡稱這些為 tools，歸在 Workflows 之下）。在這裡加入一個工作流，代理人就能在對話中呼叫它；它的描述文字，就是代理人判斷「現在是不是該用它」的依據。

畫面：AI智能助手的「行為設定」分頁，其「功能」清單
*1 「行為設定」（Behavior Settings）。2 AI智能助手的「行為設定」分頁，其「功能」清單。*

用程式碼實作：[完整流程指南](https://engineer.imbrace.co/zh-tw/sdk/full-flow-guide/)。

### MCP 連線——程式碼工具如何看到一個組織

MCP 連線讓一個 AI 程式碼工具能直接看到並變更一個組織，而不是靠別人轉述才知道。它的用途是建置：用一個位址與一把金鑰把程式碼工具指向組織，它就能在寫下任何一行內容之前，先列出組織裡已經有哪些數據表與工作流。

在側邊欄中，這位於**行動模組 > 連接模組**之下的**MCP**分頁，而且它開啟的正是你原本會直接去讀的那份指南：[engineer.imbrace.co/mcp/overview](https://engineer.imbrace.co/zh-tw/mcp/overview/)。[快速上手](getting-started.md)會一步步示範如何用這種方式，把程式碼工具連接到一個測試組織。

畫面：連接模組的 MCP 分頁，開啟 MCP 連線指南
*連接模組的 MCP 分頁，開啟 MCP 連線指南*

用程式碼實作：[MCP 伺服器指南](https://engineer.imbrace.co/zh-tw/mcp/overview/)。

### 安裝模組

安裝模組會把一整個使用案例——它的工作流、代理人設定與數據表——以單一套件的形式，一步到位複製進一個組織。它交給對方的是一個現成可用的起點，而不是一份要親手照做的說明。你的 iMBrace 聯絡窗口會把模組安裝進你的組織。

安裝完成後，它的數據表、工作流與代理人，會出現在各自平常所在的畫面裡——數據表、流程營運模組與 AI智能助手——管理員可以像對待組織裡其他任何東西一樣，在那裡檢視與編輯它們。若只需要單一個代理人，**AI智能助手**底下也有一個**「市場」（Marketplace）**分頁，提供現成的代理人範本可供套用。

畫面：AI智能助手的「市場」分頁，提供現成範本
*1 AI智能助手 > 「市場」（Marketplace）。2 現成範本卡片。*

用程式碼實作：[SDK 總覽](https://engineer.imbrace.co/zh-tw/sdk/overview/)。

## 它們如何組合在一起

來自教學課程的 Harbor Bicycle Co. 退貨櫃台，一次用到了全部五種元件。顧客與 Return Desk Assistant 對話。這個代理人負責傾聽，而它唯一的技能——一個名為 Log return request 的工作流——會在 Return Requests 這張數據表上寫入一列新的資料。另一個工作流則監看著同一張數據表：一旦有人把 Decision 設為 Approved，它就會記下是誰、在何時做的決定，接著透過電子郵件寄出確認通知給顧客。這裡完全用不到文件模型，因為沒有任何東西是以檔案形式送達的——如果退貨是以一張掃描的裝箱單送來，就會先由文件模型讀取，再變成同一張數據表上的一列資料。

Harbor 的每一個元件，都可以打包成單一模組，安裝進第二個組織，讓它的數據表、工作流與代理人設定一起帶過去，交給那個組織自己的管理員開啟與調整。而讓程式碼工具一開始就能建置出這一切的同一條 MCP 連線，之後也能用它來檢查成果：列出數據表、讀取工作流最近一次的執行紀錄。

一步一步親手建置，請見[教學課程](vibe-coding-tutorial.md)。
