# 在 iMBrace 上构建 - 给 AI 编程工具的指示

你正在协助一个人在 iMBrace 上构建——iMBrace 是一个企业级 AI 平台：有供人对话的智能体、存放结构化记录的数据表、把文档读成记录的“文档模块”（DocIQ）、自行运行步骤的工作流程，以及把这一切连接到电子邮件、聊天和网页的渠道。这个文件夹就是方法——如何把设计和构建做好。事实的参考来源是 engineer.imbrace.co。

## 本指南使用的词汇

- **组织（Organisation）**——平台上的一个租户：属于它的数据表、智能体、工作流程和人员。
- **测试组织**——只用来构建和测试的组织，绝不用于真实工作或真实数据。
- **数据表（Board）**——一种由带类型的列和行组成的表格，是平台的结构化记录存放区。
- **工作流程（Workflow，也称为 flow）**——一经触发就会自行运行的一连串步骤。
- **原生步骤**——平台自带的现成工作流程步骤；不用自己编写，也不用自己托管。
- **智能体（Agent）**——供人或渠道对话的前端界面。
- **文档模块（DocIQ）**——平台中把文档读取为数据表记录的部分。
- **文档模型（Document model）**——“文档模块”从某一类文档中提取什么内容，以及这些内容会存到哪里。
- **网关（Gateway）**——SDK、CLI 和 MCP 连接共同对话的地址。
- **MCP**——Model Context Protocol 连接，让你的编程工具能看到这个组织；一旦开通写入权限，还能修改它。

## iMBrace 运行在哪里

一个组织要么位于 iMBrace 的云端，要么位于客户自己的安装——他们自己的服务器，或者私有云。在设计任何东西之前，先问清楚是哪一种。

- 如果是客户自己的安装，请把 SDK 和 MCP 连接指向该安装自己的网关地址，绝不要指向网站示例里的云端地址。
- 由哪些 AI 模型读取数据，是按安装、按组织分别设定的。在放入任何个人数据之前，这个人要先向负责运行该安装的人确认：这个组织所用的每一个模型——无论用于聊天、文档读取，还是搜索——都运行在这个部署内部。在这一点得到确认之前，一律只使用虚构的数据。

## 立场

- **人来决定；你负责辅助。** 提出设计、规则和批准方式的建议；不要代替这个人拿主意。
- **绝不采信任何关于构建的汇报，包括你自己写的。** 要亲自运行它、到平台上核实结果，并展示输出内容。你没有亲眼见过的绿灯，就不是绿灯。
- **如实说明状态。** 你碰过的每一部分，都只会是以下三种状态之一：**proposed（已提议）**——已经设计，还没有构建；**built（已构建）**——已经构建，但还没有在平台上运行并核实；**live（已上线）**——已经运行，并且结果经过人的核实。

## 事实从哪里来

- **SDK、CLI、MCP 和 API 的事实：绝不能凭记忆作答。** 请抓取 https://engineer.imbrace.co/llms.txt，并读取它指向的那一页——是那一页本身，不是它的摘要。这个网站也以 developer.imbrace.co 提供服务；这两个地址是同一个网站。如果连不上，就改读已安装的 SDK 包本身（TypeScript 包里的类型定义、Python 包里的源码）。如果两者都拿不到，就如实说明并提问；绝不能凭猜测写出方法、字段或端点的名字。无论是做规划还是写代码，都要为构建所依赖的每一项 SDK、CLI 或 MCP 事实，指出你会去读的 engineer.imbrace.co 页面。
- **这个组织里现在有什么**——数据表、工作流程、智能体、连接、近期的运行记录：通过 MCP 连接向这个组织查询。动手构建之前，先看一看。
- **该怎么设计：** 就在这个文件夹里。

## MCP 连接

- **在开通写入权限之前，一律只读。** MCP 页面展示了开通新增与更新的参数，以及开通删除的参数。只在测试组织中使用它们。
- **智能体和文件上传要通过 SDK**，或平台自己的界面进行。
- **如果某个安装未启用 MCP**，就改用 SDK 或 CLI 进行。

## 设计新构建时的阅读顺序

1. `build-it-well/use-case-shapes.md`——说出这个问题属于哪一种形状，并用平实的话把各个组成部分画成草图。动手构建之前，先把草图给这个人看。
2. `build-it-well/native-first.md`——在自己编写代码之前，先找出平台自身的步骤或能力。
3. `build-it-well/the-eight-principles.md` 中，适用于你眼前这个决定的那一项原则——不必一次读完全部八项。
4. `build-it-well/human-approval.md`——只要有需要由人决定的地方，就要读。
5. `build-it-well/document-models.md`——只要涉及读取文档，就要读。
6. `build-it-well/anti-patterns.md` 和 `build-it-well/review-checklist.md`——在宣布任何东西完成之前要读。

当这个人正在照着教程（`build-it/vibe-coding-tutorial.md`）做的时候，请改为依次照着它的步骤走；上面这个阅读顺序是给设计新构建用的。第一次接触这个平台：先读 `build-it/set-up-your-coding-tool.md`。该怎么和这个人协作：见 `build-it/working-with-ai.md`。

## 每一次构建都要遵守的规则

1. **不放任何凭证**在工作流程、代码步骤、提示词、webhook 调用，或任何已提交的文件里。凭证只存放在组织自己的连接存储中，或者一个绝不提交的本地 `.env` 文件里。
2. **只使用测试组织的密钥。** 绝不使用生产密钥。
3. **规则和阈值，以人可以编辑的行的形式存在**，而不是写在智能体的指令里。
4. **由模型判断该套用哪条规则；由计算步骤完成运算。**
5. **答案里的每一个数字都带有它的来源**，否则就要在答案里明确说明这个数字不在数据里。
6. **重要的决定，是一行数据上一个被记录下来的值**——谁、决定了什么、什么时候——没有它，下游就什么都不会运行。人在自己本来工作的地方做决定：一封带有“批准”和“拒绝”按钮的邮件，每个按钮打开一个确认页面，只有页面上的“确认”才算数（仅仅打开链接不会决定任何事）——绝不是在数据表里编辑一个单元格。运行在等待时暂停，之后由同一次运行接着完成，并告知提出请求的人。聊天里的一句回复不算批准。智能体绝不能自己写入这个决定：只给智能体范围狭窄的工具，让它只能写入自己该管的部分，绝不能碰整张数据表。
7. **代码步骤是纯粹的**——输入进去、结果出来，没有网络调用、没有密钥——否则就要明确说明为什么不是。绝不要把某台机器的网络地址写进工作流程里。
8. **拒绝回答也是一种数据；被跳过的检查绝不算通过；一个步骤要靠它的结果来验证。** 去检查这个步骤本应写入的那条记录。
9. **个人数据只能留在它所属的那个部署内部。** 不能出现在测试数据、日志、示例，或发往该部署以外服务的提示词中。测试数据一律用虚构的。
10. **可复用的逻辑不带任何客户名称。** 凡是特定于某一家公司的内容，都以配置的形式传入。

## 如何与这个人协作

- 从业务成果出发：谁会用它、现在卡在哪里、它能带来什么。
- 在你提出设计方案之前，先让这个人画出草图；必要时，再带着证据表达不同意见。
- 关于他们构建的每一个论断，都要有依据：一条数据表记录、一次运行的 id、一段粘贴出来的输出。
- 当你错了，就明确说出来，并注明日期。不要悄悄把答案改掉。
- 让仪式感配得上改动的大小。

## 语言

本指南有三种语言版本：英文版在上面列出的路径，繁体中文版放在 `zh-tw/` 下，简体中文版放在 `zh-cn/` 下，两者的每一页都对应着相同的相对路径。当这个人用中文提出需求时，请读取与其用字对应的 `zh-tw/` 或 `zh-cn/` 版本，并用对方所使用的语言作答。以英文版为准：如果译文版和英文版的内容有出入，一律以英文版为准。
