# 人工批准

每一个重要的构建，都有这样一个时刻：必须有人点头，某样东西才能发出去。这个决定本身，无论在哪个构建里都是同一回事；但由谁在哪里做出它，每个用例都可以不同。

## 决定是一回事，做出决定的场合是另一回事

决定这部分的工作，是从底层记录中算出应当发生什么，如果还没有人做出决定就拒绝继续，并记下是谁决定的、决定了什么、什么时候决定的。这部分不会因构建而改变。

而做出决定的场合——一个人具体在哪里、以什么方式做出这个决定——则是一项设计选择，需要按每个用例分别决定，依据是这个人本来就在哪里工作，以及构建在等待期间应当如何表现。

## 人可以在五个地方做出这个决定

| 场合 | 运作方式 | 适用场景 |
|---|---|---|
| **记录上的一个字段** | 一个人在数据表或列表上切换一个状态字段；这个字段一变化，下一步就会自动触发 | 审核人本来就每天在这张数据表上工作。不需要任何自定义界面，也是迄今为止最常见的场合 |
| **一次真正等待的暂停** | 构建会真正挂起这次运行，直到有人处理完为止，而不是靠轮询或猜测 | 流程在有人采取行动之前绝不能继续 |
| **一次性链接** | 一个带签名的链接，每种可能的结果各对应一个；打开它会显示详情，在上面确认就会写入这个决定 | 审核人完全在别处，为他们专门搭建一个门户网站并不划算 |
| **聊天中的一张批准卡片** | 构建会在审核人已经在用的渠道里发布一条带按钮的消息；点击按钮后，运行随即恢复 | 审核人本来就活跃在那个渠道里 |
| **对话中的一条指令** | 一位经过验证身份的人，输入一句批准的话，并指明具体的项目；系统会把它记录在对应的那一项上 | 审核人本来就在与一个智能体对话，并且这个渠道能够验证对方的身份 |

这五种方式，最终都会走到同一个地方：一条被记录下来的决定，绑定到具体的一项，并附有谁决定的、什么时候决定的。

记录下决定并不是最后一步。无论用的是哪种场合，一旦决定落地，流程都会自行接着往下走——完成它一直在等待的那项工作，或者把结果告诉提出请求的人——不需要任何人特意留意，再回头去问一次。

具体有哪些场合可用，取决于你的安装环境和版本；你的 iMBrace 联系人可以为你确认。记录上的字段是使用最广、也最适合入手的场合。无论选择哪种场合，在依赖它之前，都要亲自以审核人的身份走一遍这条路径：他们被通知到，他们打开这一项，他们记录下决定。

## 一种行之有效的组合：用数据表的一列，恢复一个暂停的工作流程

当流程必须真正等待、而审核人又是在数据表上工作时，可以把前两种场合组合起来使用。工作流程创建一个任务（Todos 步骤），通知审核人——比如通过电子邮件，附上指向这条记录的链接，而绝不是一个能直接做出决定的链接——然后暂停等待。审核人在这条记录的一个单选列里，选择批准或拒绝。一个绑定在这一列上的自动化，会恢复被暂停的任务。随后由工作流程——而不是那次编辑本身——写入结果，这样，能写入这个决定的，就只有唯一一个地方。

直接通知审核人。一个正在等待的任务，只有在审核人知道它存在时才会往前走，所以那条带有记录链接的消息，是这个模式中必不可少的一步，而不是可有可无的附加项。

## 不能通融的规则

**在聊天里随手打出一句友善的“好的”，单凭它本身，并不算一个决定。** 它只是流程控制——也许能让对话继续往下走——但仅凭它自己，不会留下任何可以长期保存的记录，让人在日后指着它说：这件事经过批准，是这个人批的，是在这个时间批的。

前面提到的指令场合，并不是这条规则的例外。恰恰相反，它正是让一条聊天消息能够算作一个决定的原因：系统会把它捕获为一条结构化的记录，绑定到具体的一项，并附有经过验证的发送者身份，而不是任其停留在聊天记录里。一句光秃秃的“好的”，如果没有任何东西把它和具体的一项绑在一起，根本不会被当作一个决定接受。

还有两条同样值得牢记的规则：

- **关卡会自己算出答案。** 它会根据底层记录重新计算结果，而不是相信同一次交互中刚刚被告知的那个数字。一个别人说什么就信什么的关卡，会毫不犹豫地批准一个错误的数字。
- **没有决定，就没有输出。** 不设默认值，也不设一个等一段时间就放行的超时机制。只要还没有人做出决定，就什么都不会发出去。

## 让关卡真正站得住的四个细节

- **数据表的编辑，要保存之后才会生效。** 从已保存的状态来测试这个关卡，并在给审核人的说明里写明要按下**保存**（Save）。
- **决定链接要先展示内容，只有在确认之后才会生效。** 打开一个链接——无论是本人打开，还是邮件扫描程序或预览功能打开——都绝不能因此就记录下一个决定。决定链接只发给审核人，并且要让这些链接、以及任何可能单凭自身就做出决定的标识符，都不出现在记录本身里。
- **智能体绝不能有权写入这个决定。** 用来记录决定的那些列，要设计成在记录创建时就取好初始值，并拒绝之后来自智能体的任何写入——只给智能体范围狭窄、根本够不到这些列的工具。
- **“尚无结论”绝不能被看成“已通过”。** 一项还没运行、或者运行失败的检查，会让这条记录看起来和真正通过的记录一模一样。要给每一条记录都打上结论——干净无误的记录也不例外——并让之后的每一步都等待这个结论，没有它就拒绝继续。

## 证明关卡是真的接上了，而不只是摆在那里

一个控制点的价值，取决于它到底绑定了什么。要确认这个状态字段在它能取到的每一个值上，都会触发一个真实的自动化，而不只是你原本预期的那几个值。

把这个场合接到真正依赖它的东西上，并且完整走一遍从头到尾的整条路径——包括“还没有人做出决定”这种情况——然后才能说这个批准步骤已经做完了。
