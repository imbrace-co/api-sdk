title: 審查清單
description: 依循八大原則進行審查，寫成一份你可以在上線之前，對自己的建置親自跑一遍的清單。
---

這份審查清單，和內部使用的審查完全相同，只是改寫成你可以親自對自己的建置執行的版本。大約需要一小時，而且如果執行審查的人不是建置這個東西的人，會有用得多。

## 如何執行

1. 把下面的評分表複製一份，放在你正在審查的建置旁邊。
2. 依序檢視每項原則的問題，這些問題取自[八大原則](/learn/build-it-well/the-eight-principles/)。
3. 為每個問題評分：<strong>已達成</strong>、<strong>部分達成</strong>、<strong>尚未達成</strong>，或<strong>不適用</strong>。
4. 每個分數都需要一個<strong>佐證</strong>——某個具體、能證明這個分數的東西：一筆特定的紀錄、一段你親眼看著發生並貼上來的結果、一張實際行為的截圖。沒有任何佐證的分數，只是一個意見，不是審查。
5. 任何評為<strong>尚未達成</strong>的項目，要嘛在上線前修好，要嘛就寫一則附上日期的說明，記下是誰接受了這個缺口，以及原因。

## 讓這件事值得做的幾條規則

- <strong>審查者不是建置者。</strong> 審查自己作品的人，往往只找得到自己原本就已經知道的問題。
- <strong>實際執行，不要只是看過就算。</strong> 不要因為一項測試看起來應該會過，就假設它真的會過。實際執行它，親眼看結果。
- <strong>「不適用」需要理由。</strong> 這是一個正當的分數，但沉默不算——寫下為什麼這個問題在這裡不適用。
- <strong>部分達成不等於通過。</strong> 它是一個有名字、有負責人的缺口，最好還附上一個日後要重新檢視的日期。
- <strong>這份審查的對象是建置，不是人。</strong> 目的是讓成果變得更好，而不是對建置的人做出評斷。

## 1. 溯源性

| # | 問題 | 分數 | 佐證 | 備註 |
|---|---|---|---|---|
| 1 | 不需要別人幫忙，能不能從輸出結果中的一個數字，直接追到它背後的紀錄？ | | | |
| 2 | 答案有沒有附上「截至」的日期？ | | | |
| 3 | 被引用的那一行，有沒有對照來源、並附上位置來證明？ | | | |
| 4 | 當資料無法回答這個問題時，使用者會看到什麼？ | | | |
| 5 | 每一行被引用的內容，是不是真的支持它的結論，還是只是剛好出現在來源裡？ | | | |

| # | 問題 | 分數 | 佐證 | 備註 |
|---|---|---|---|---|
| 1 | 任何被標示為「共用」的東西，請說出兩個真實、各自獨立的使用情境。 | | | |
| 2 | 有沒有任何變體，實際上是靠修改內容做出差異，而不是靠設定？ | | | |
| 3 | 一個元件能不能在沒有正式帳號、也沒有網路連線的情況下，單獨被測試？ | | | |
| 4 | 這個建置裡，有沒有任何東西找不到一個真實、指名道姓的使用者？ | | | |
